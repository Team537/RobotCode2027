# Fuse vision first, then automate everything

Top FRC teams are hard to beat not because of one secret library but because they stack five layers on top of a well-tuned swerve: a field pose that stays correct all match (AprilTag vision fused into the pose estimator), a drive-to-pose primitive that turns that pose into one-button alignment and sensor-gated autos, a superstructure state machine that coordinates mechanisms, structured logging and simulation that let them test without a robot, and CI plus a PR workflow that keeps the code from rotting. Team 537's codebase (git HEAD `262c4c6`) has the swerve and every hook it needs, including an unused `addVisionMeasurement`, a wired-up `AutoBuilder`, and a `photonlib v2026.3.4` vendordep, but none of the layers above it, and the drivetrain itself carries configuration hazards (mixed Kraken/NEO drive motors behind a single shared PID file, no current limits, placeholder PathPlanner physics) that will undermine everything built on top. The recommended order is therefore: fix the drivetrain config and add input shaping and acceleration limiting (days), bring up AprilTag localization on two global-shutter cameras and fuse it with distance-scaled standard deviations (one to two weeks including hardware), build a `DriveToPose` command and a first PathPlanner auto that keeps a tag in view (one to two weeks), then layer logging, a sim-first habit, CI, and a superstructure skeleton (days each). Because 2027 is a hard control-system break (roboRIO illegal, SystemCore, Java 25, `org.wpilib` package rename, Commands v3), invest offseason effort in architecture and habits rather than roboRIO-specific APIs, and plan a December port to the WPILib 2027 beta so the team arrives at kickoff with a working project. Two things to flag up front: AdvantageKit's deterministic replay is explicitly incompatible with YAGSL's direct-hardware design, so the team should use DogLog or Epilogue instead; and no public team repository was found running a Kraken/NEO drive-motor mix on one swerve, so the mixed-motor guidance here is reasoned from specs and library structure, not from a proven precedent.

## Elite teams win on a trusted pose and a state machine, not a secret library

The 2025–2026 public code of 6328, 254, 1678, 2910, 3847, and 581 converges on the same architecture even though they pick different libraries. 254's 2025 README describes a `RobotContainer` plus `RobotState` tracking robot and game-piece position, every subsystem following "the AdvantageKit IO pattern with separate hardware and simulation interfaces," a `SuperstructureStateMachine` with modes, `ModalControls` for driver mode switching, auto-align to every scoring location "with dynamic target selection based on field position," and A* pathfinding autos with "real-time path recalculation based on game piece acquisition success" ([Team254/FRC-2025-Public](https://github.com/Team254/FRC-2025-Public)). 1678's 2026 robot runs a "fully custom targeting system" that picks where to shoot from the robot's field position, uses LEDs so drivers avoid "having to look away from the robot to know what state it's in," and needs only "a single controller to utilize all of its functionality," with one Limelight 4 doing AprilTag pose estimation ([frc1678/C2026-Public](https://github.com/frc1678/C2026-Public)). 3847 describes "Heavy use of Triggers as states for activating commands," which "all but eliminates the need for complex multi-mechanism command groups," plus a `Mechanism` wrapper over TalonFX, simulation classes, DogLog logging, Spotless, SpotBugs, and CI ([2026-Spectrum README](https://github.com/Spectrum3847/2026-Spectrum)). Every one of these repos has CI and a formatter; 1678's `tests.yml` runs `./gradlew test` in the `wpilib/roborio-cross-ubuntu` container on every push and PR ([frc1678 tests.yml](https://github.com/frc1678/C2026-Public/blob/main/.github/workflows/tests.yml)).

The driver-facing capabilities that separate these robots from mid-tier ones are almost all automation built on a trusted field pose: one-button auto-align, dynamic target selection, single-controller operation, and state-reflecting LEDs. 2910's 2025 release is instructive because it shows how little machinery is actually required: auto-align was "a simple PID controller with velocity caps" with "friction compensation specifically for auto-alignment to prevent stalling near targets," and localization used "hard resets of odometry based on AprilTag camera observations," performed "only during auto-scoring when stability is optimal" ([Team 2910 Code Release 2025](https://www.chiefdelphi.com/t/team-2910-code-release-2025/503697)). The July 2026 "Success In Autonomous" thread adds the two rules that matter most for a team starting out: "Making sure you can (almost) always see a tag throughout the auton will make sure you stay on track," and "You're not going to get your robot to perform tenfold better in auto than it does in teleop" ([CD: Success In Autonomous](https://www.chiefdelphi.com/t/success-in-autonomous/522311)).

Measured against that stack, 537's code is a clean but empty foundation. The survey of `src/main/java/frc/robot/` shows five Java files, one subsystem (`subsystems/swervedrive/SwerveDriveSubsystem.java`), a stock `Robot.java`, no `commands/` package, no tests, no CI, no logging framework beyond YAGSL's own telemetry, and a `Robot.java` whose disabled/teleop/sim hooks are empty. `addVisionMeasurement(Pose2d, double)` exists at `SwerveDriveSubsystem.java:139-141` but nothing calls it, `AutoBuilder.configure` is set up at lines 53–74 but `src/main/deploy/pathplanner/` holds no `.path` or `.auto` files so the chooser offers only "None," and `RobotContainer.java:25-39` maps a single Xbox controller through a YAMS `SwerveInputStream` with a 0.05 deadband and alliance-relative control but no slew limiting, precision mode, heading lock, or operator controller. ## The drivetrain config has hazards that must be fixed before anything else

Everything downstream (odometry, vision fusion, PathPlanner's physics-based trajectory generation) assumes the drivetrain reports and tracks velocity honestly, and the current JSON does not guarantee that. The survey found that `src/main/deploy/swerve/base/modules/` configures front-left and front-right drive as `talonfx_krakenx60` (CAN IDs 2, 4) and back-left and back-right as `sparkmax_neo` (IDs 6, 8), all steer as `sparkmax_neo550` (IDs 3, 5, 7, 9), with REV Through Bore absolute encoders, while `src/main/deploy/swerve/README.md` calls the modules "REV MAXSwerve." Before tuning anything, physically confirm which motors are on the robot; the JSON and README disagree, and every recommendation below depends on which is true.

**Mixed Kraken/NEO drive motors are the single largest uncertainty in this codebase.** No public 2025/2026 team repository was found that runs Kraken and NEO drive motors on one swerve; the closest precedent, 2910 mixing MK4i and MK4n modules, concerns different gear ratios on the same motor type, with the advice that "you just have to tune the modules in code for the different steering ratios" ([CD: Combining MK4i with MK4n](https://www.chiefdelphi.com/t/combining-mk4i-with-mk4n/491911)). CTRE's generator will not build a mixed drivetrain at all; "If you want a mixed drivetrain with both Kraken and NEOs, you'll probably have to use YAGSL" ([CD: CTRE Swerve Request](https://www.chiefdelphi.com/t/ctre-swerve-request/511834)), so YAGSL is the right choice, but YAGSL's documented starting gains differ by vendor: drive `p: 0.0020645` for SparkMax versus `p: 1` for TalonFX, and angle `p: 0.01` for SparkMax versus `p: 50, d: 0.32` for TalonFX ([YAGSL docs](https://yagsl.yassrobotics.com/llms-full.txt)). The repo's single `pidfproperties.json` sets drive `p=0.9, d=0.3` for all four modules, which is close to the TalonFX starting point and roughly 400 times the SparkMax one. The practical consequences, reasoned from the specs and library structure rather than a proven precedent: the NEO's lower free speed (5,676 vs 6,000 RPM) and far lower stall torque (2.6 vs 7.09 N·m, per a secondary comparison page to be verified against vendor sheets) mean the rear wheels saturate first ([FRC 8569 motor comparison](https://frc8569.readthedocs.io/en/latest/MotorTutorial/MotorComapre.html)), so set `SwerveDriveConfig.withMaximumChassisSpeed`/`withMaximumModuleSpeed` to the NEO-limited value (with 4.71:1 gearing on 3-inch wheels that is about 4.8 m/s free, less under load), rely on characterized per-vendor kS/kV feedforward with a small P rather than a large shared P, and consider lowering the Kraken stator limit (60–80 A instead of CTRE's 120 A reference) so the front cannot drag the rear and yaw the chassis under full throttle. Verify in the YAMS source whether `SmartMotorController` normalizes gains across vendors before assuming one `p` value means the same thing on both; this was not confirmed. If any of this proves unmanageable, the cleanest fix is hardware: four matching drive motors.

The remaining config fixes are quick and well-sourced. `physicalproperties.json` sets no current limits, ramp rate, or coefficient of friction. REV's locked-rotor test shows a NEO 550 at the 80 A default fails in about 2.0 s, at 40 A in about 27 s, and at a **20 A** Smart Current Limit survives the full 220 s test, so set the steer current limit to 20 A ([REV NEO 550 locked rotor testing](https://revrobotics.com/neo-550-brushless-motor-locked-rotor-testing)). CTRE's reference swerve uses a 120 A slip current for drive and a 60 A steer stator limit because "Swerve azimuth does not require much torque output" ([CTRE Swerve Builder API](https://v6.docs.ctr-electronics.com/en/docs-2026-beta/docs/api-reference/mechanisms/swerve/swerve-builder-api.html)). The README already flags steer `p=0.01` as "likely far too low"; community threads attribute straight-line twist to under-gained steering ("increasing steering gains and using outboard positional control helps") ([CD: Drift issues](https://www.chiefdelphi.com/t/drift-issues-with-ctre-swerve-code-need-pro/472096)), so raise it until the module tracks without oscillation, and confirm the NEO 550 loop closes on the Through Bore rather than the motor encoder. Enable `ChassisSpeeds.discretize` via `SwerveDriveConfig.withDiscretizationTime(Seconds.of(0.02))` in `SwerveDriveSubsystem.java:38-44`; WPILib's `discretize` is the standard fix for the sideways skew that appears when translating and rotating simultaneously ([WPILib ChassisSpeeds](https://github.wpilib.org/allwpilib/docs/release/java/edu/wpi/first/math/kinematics/ChassisSpeeds.html)), and since YAMS exposes it as an `Optional<Time>` it is probably off unless set (an inference; check `SwerveParser` to confirm). YAGSL's own drift guide prescribes a strict tuning order, drive/angle PID first, then vision std devs, then discretization, then gyro angular-velocity scale factor, and warns that "Changing an earlier step...means redoing every step after it" ([YAGSL: Swerve Drive Drift](https://yagsl.yassrobotics.com/reference/swerve-drift-causes.md)).

Finally, fix `src/main/deploy/pathplanner/settings.json` before drawing any path. It currently declares `driveMotorType: "NEO"` while the front motors are Krakens, and the README admits the mass (74.088 kg), MOI (6.883), and 0.9 m bumpers are placeholders. Since v2025.1.1, PathPlanner generates trajectories with "Motor torque-based acceleration limits respecting swerve dynamics" and "Traction control" ([PathPlanner releases](https://github.com/mjansen4857/pathplanner/releases)), so motor type, current limit, mass, MOI, and COF directly bound the accelerations of every path. The docs want mass "including bumpers and battery," MOI derived from sysId (the ratio of the drive motors' angular to linear acceleration constants), "True Max Drive Speed" measured under load on a charged battery or estimated at 85% of free speed, and COF from the wheel vendor or tuned "until wheels no longer slip" ([PathPlanner: Robot Config](https://pathplanner.dev/robot-config.html)). The current `maxDriveSpeed: 4.81` is the NEO free speed, not a loaded speed; 85% of it is about 4.1 m/s. With mixed motors, PathPlanner supports only one motor type, so configure the weaker one (NEO) with a conservative current limit until sysId data exists. YAGSL also warns that wheel diameter lives in both the YAGSL JSON and PathPlanner settings and must be kept in sync "or PathPlanner's paths and YAGSL's own odometry will disagree" ([YAGSL: Set up PathPlanner](https://yagsl.yassrobotics.com/how-to-guides/setup-pathplanner.md)).

## Smooth the drivetrain by shaping inputs, limiting the velocity vector, and reading tilt off the Pigeon

The YAMS `SwerveInputStream` in `RobotContainer.java:25-39` is not the legacy `swervelib.SwerveInputStream` that most web tutorials describe. Verified with `javap` against the `YAMS-java-2026.10.03.jar` in the local Gradle cache, the stream exposes `withDeadband`, `withScaleTranslation(double)`, `withScaleRotation(double)`, `withCubeTranslationControllerAxis()`, `withCubeRotationControllerAxis()`, `withAllianceRelativeControl()`, `withRobotRelative()`, `withHeadingControl(BooleanSupplier)`, `withControllerHeadingAxis(DoubleSupplier, DoubleSupplier)`, `withAim(Supplier<Pose2d>, BooleanSupplier)`, `withTranslationOnly(BooleanSupplier)`, `withMaximumLinearVelocity`, `withMaximumAngularVelocity`, and `clone()`, and it has **no slew or acceleration limiting and no `driveToPose`**. Legacy names like `scaleTranslation`, `headingWhile`, `aimWhile`, and `driveToPose(...)` that appear in the older javadoc ([Legacy YAGSL SwerveInputStream](https://broncbotz.org/YAGSL-Lib/docs/swervelib/SwerveInputStream.html)) do not exist in this project's pinned version; students copying examples from Chief Delphi will hit compile errors.

The immediate, low-risk wins in `RobotContainer.java` are to raise the deadband to 0.1, add `withCubeTranslationControllerAxis()` and `withScaleRotation(≈0.6)`, and build a precision mode by cloning the base stream: `SwerveInputStream slow = base.clone().withScaleTranslation(0.3).withScaleRotation(0.4)` selected with `driveFieldOriented(() -> precisionTrigger.getAsBoolean() ? slow.get() : fast.get())`. This follows what 6328's 2025 `DriveCommands` does: a **0.1 deadband applied to the joystick magnitude** (`Math.hypot(x, y)`), the magnitude squared while the direction is preserved, and omega processed as `omega * omega * Math.signum(omega)` ([6328 DriveCommands.java](https://github.com/Mechanical-Advantage/RobotCode2025Public/blob/main/src/main/java/org/littletonrobotics/frc2025/commands/DriveCommands.java)). The same file shows how 6328 handles a raised elevator: it does not slew-limit; it scales rotational speed to **20%** (`maxExtensionAngularVelocityScalar = 0.2`) when the elevator is extended. Because the YAMS scaling methods take fixed doubles, continuous elevator-height scaling must be done on the stream's output (`ChassisSpeeds.times(k)` with a `DoubleSupplier` reading mechanism height), not on the stream itself.

For a delicate game piece, the key control is acceleration limiting on the velocity vector, not on the raw joystick axes. Because the stream is a `Supplier<ChassisSpeeds>`, the clean insertion point is a wrapper: `m_swerve.driveFieldOriented(() -> limiter.apply(m_driveStream.get()))`. The limiter should cap the per-loop change of the `(vx, vy)` vector's magnitude while preserving its direction (the polar approach), with a separate scalar cap on omega, using `maxAccel * 0.02` per cycle from a `DoubleSupplier` so the limit can drop as a mechanism rises. This generalizes the simplest pattern in the Chief Delphi "Dynamic acceleration limits" thread (`Vf = Vi + a*t` with `t = 0.02 s` applied per loop so the limit can change every cycle without persistent state) ([CD: Dynamic acceleration limits](https://www.chiefdelphi.com/t/dynamic-acceleration-limits-how-do-you-implement-them/491287)). Limiting x and y independently with two WPILib `SlewRateLimiter`s distorts the direction of diagonal moves and makes the effective limit depend on heading because the stream output is field-relative; that argument is from the geometry and from the fact that 6328 and the AdvantageKit template shape the magnitude, not from a single authoritative thread, and some teams (2338) do use three per-axis `SlewRateLimiter`s successfully ([CD: keep your robot from tipping](https://www.chiefdelphi.com/t/programming-wise-how-do-you-keep-your-robot-from-tipping/520929)). Reset the limiter's state from `swerve.getFieldRelativeSpeed()` when the command starts so it does not fight an already-moving robot, keep the deceleration cap separate and equal to or slightly above the acceleration cap so the driver can still stop, and follow the "Finding Your Robot's Limits" advice to "start with excessively-low limits, and crank them up to see which requirement gets missed first" among mechanism limits, brownout, tipping, driver comfort, and wheel slip ([CD: Finding Your Robot's Limits](https://www.chiefdelphi.com/t/finding-your-robot-s-limits/507999)). No top team publishes numeric teleop acceleration limits; 6328's 3.5 m/s² teleop figure is for auto-align profiles, not driver input.

Heading hold belongs in the same wrapper: when `|omega_input|` falls below the deadband, latch the current heading and substitute `omega = headingController.calculate(current, target)`. The AdvantageKit template's `joystickDriveAtAngle` gives tested starting values, a `ProfiledPIDController` with **kP 5.0, kD 0.4, 8 rad/s max velocity, 20 rad/s² max acceleration**, `enableContinuousInput(-Math.PI, Math.PI)`, reset to the current rotation on command start ([AdvantageKit DriveCommands.java](https://github.com/Mechanical-Advantage/AdvantageKit/blob/main/template_projects/sources/spark_swerve/src/main/java/frc/robot/commands/DriveCommands.java)). Chief Delphi confirms "If drift is a big issue, you can run a heading PID to maintain the robot's heading after you stop turning" ([CD: Robot twists while driving straight](https://www.chiefdelphi.com/t/robot-twists-while-driving-straight/514165)). YAMS's `withHeadingControl` plus `withControllerHeadingAxis` provides joystick-direction heading mode but not "hold last heading when idle," so this must be implemented in the wrapper; a short 0.1–0.3 s delay after stick release before latching avoids snap-back (common practice, not sourced).

The Pigeon 2 on CAN ID 42 (`swervedrive.json:3-9`) can do more than yaw. Phoenix 6's `Pigeon2` exposes `getPitch()`, `getRoll()`, `getAngularVelocityXWorld/YWorld/ZWorld()`, `getAccelerationX/Y/Z()`, `getGravityVectorX/Y/Z()`, and `getNoMotionCount()` ([Phoenix 6 Pigeon2 Javadoc](https://api.ctr-electronics.com/phoenix6/stable/java/com/ctre/phoenix6/hardware/Pigeon2.html)). Three practices matter. First, after the Pigeon's mounting is final, run Tuner X mount calibration with the robot "level and stationary"; it computes offsets "to ensure that Pose, Pitch and Yaw is 0 when the robot is considered 'flat'" ([CTRE Pigeon 2 calibration](https://v6.docs.ctr-electronics.com/en/latest/docs/tuner/pigeon-cal.html)). Second, never fix field orientation mid-match with `pigeon.reset()` or `setYaw()`; the raw yaw "is unaffected by things like resetPose or seedFieldCentric," so reset through `SwerveDrive.resetOdometry(Pose2d)` and use the pose estimator's rotation for vision ([CD: CTRE Swerve Pose Estimation](https://www.chiefdelphi.com/t/ctre-swerve-pose-estimation/516809)); the existing `zeroGyro` on Start is fine for pre-match squaring. Third, if a consistent yaw error appears, Team 2102 measured **1.5–2° per full rotation** across multiple Pigeons and CTRE staff recommended `GyroTrimConfigs` to correct it ([CD: Pigeon 2 Inaccuracy Issues](https://www.chiefdelphi.com/t/pigeon-2-inaccuracy-issues/502089)). For tilt-aware driving with a fragile load, construct a `Pigeon2(42)` in code for pitch/roll (YAGSL only consumes yaw), raise the consumed signals with `BaseStatusSignal.setUpdateFrequencyForAll(100, ...)` and `refreshAll` once per loop, staying at 100 Hz on a roboRIO CAN 2.0 bus with eight motor controllers because CTRE warns of "indeterminate behavior at high utilization rates (>90%)" ([CTRE Status Signals](https://v6.docs.ctr-electronics.com/en/latest/docs/api-reference/api-usage/status-signals.html)). Then, as a second line of defense behind acceleration limiting, scale the commanded acceleration down as |pitch| or |roll| rises and optionally add a proportional corrective velocity; the open-source AntiTipping library uses a **3.0° threshold, kP 0.04, and a 2.5 m/s cap**, taking `imu::getPitch` and `imu::getRoll` suppliers and outputting `ChassisSpeeds`, and one reply noted IMU correction handles "running into something up high that applies a tipping force" better than acceleration limits alone ([CD: Introducing AntiTipping lib](https://www.chiefdelphi.com/t/introducing-antitipping-lib/508284)). Only a handful of teams do this (340 and the AntiTipping author are the documented ones), so treat it as optional polish after the limiter works.

## Two global-shutter cameras and distance-scaled std devs give a pose you can trust

Hardware first, because nothing in `Vision.java` matters without it. The two realistic options are PhotonVision on an Orange Pi 5 with Arducam OV9281 global-shutter cameras, or a Limelight 4. The Orange Pi 5 is "the recommended coprocessor for most teams" at about $99 ([CD: Limelight vs Photonvision](https://www.chiefdelphi.com/t/limelight-vs-photonvision/452856)), PhotonVision recommends global-shutter cameras "in all cases" with roughly 100° diagonal FOV for AprilTags and explicitly does not support Logitech or built-in webcams ([PhotonVision: Selecting Hardware](https://docs.photonvision.org/en/latest/docs/hardware/selecting-hardware.html)), and maintainers recommend only **two tag cameras per Orange Pi 5**, each running around 30 FPS at 1280x720 ([CD: Orange Pi 5 Camera Limit](https://www.chiefdelphi.com/t/orange-pi-5-camera-limit/482792)). The Limelight 4 costs **$489** at AndyMark ($660 with the Hailo-8 accelerator) ([AndyMark: Limelight 4](https://www.andymark.com/products/limelight-4)), has an onboard IMU for MegaTag2, and dropped PoE so it needs a separate power run ([CD: Introducing Limelight 4](https://www.chiefdelphi.com/t/introducing-limelight-4/480329)); one team reported it "really just works and has worked flawlessly," while another got an uncalibrated Orange Pi/PhotonVision setup working in two hours at "1/3 - 1/4 the price" ([CD: Choosing a Localization Processor](https://www.chiefdelphi.com/t/choosing-a-localization-objectdetection-processor/506193)). The choice turns on budget and mentor Linux comfort; the `photonlib v2026.3.4` vendordep already in the repo and the free YAGSL-Example reference code tilt the recommendation toward PhotonVision on an Orange Pi 5 with two cameras, with a Limelight 4 as the lower-effort alternative if the budget exists. Real-world PhotonVision 2025 reliability was good but not perfect: about 1 in 50 boot failures, 1 in 50 matches with a camera stream shutting down, USB enumeration swaps causing "camera mismatch," and an OV9281 exposure bug needing a manual toggle ([CD: PhotonVision 2025 Feedback](https://www.chiefdelphi.com/t/photonvision-2025-feedback/500533)), so build a pre-match checklist.

Mount two front-corner cameras yawed outward and pitched up, which is what both the top reference and the YAGSL example do: 6328's 2025 competition robot put front-left and front-right cameras at (0.2794, ±0.2286, 0.211 m), pitch −25°, yaw ∓20°, at 1600x1200, plus a rear camera with a 1.25 std-dev factor, and their 2026 robot runs four cameras with "fudge factor" pitch offsets, which shows that even top teams correct CAD transforms empirically ([6328 2025 VisionConstants](https://raw.githubusercontent.com/Mechanical-Advantage/RobotCode2025Public/main/src/main/java/org/littletonrobotics/frc2025/subsystems/vision/VisionConstants.java); [6328 2026 VisionConstants](https://raw.githubusercontent.com/Mechanical-Advantage/RobotCode2026Public/main/src/main/java/org/littletonrobotics/frc2026/subsystems/vision/VisionConstants.java)). Calibrate each camera at the resolution it will run, with a ChArUco board ("We strongly recommend that teams use ChArUco boards instead!"), at least 12 varied shots, targeting mean reprojection error under 1 pixel ([PhotonVision: Calibration](https://docs.photonvision.org/en/latest/docs/calibration/calibration.html)); 2025 users said calibration's importance needs "size 70 font, and bolded."

The code is largely portable. YAGSL-Example ships a `Vision.java` with a `Cameras` enum holding per-camera `Rotation3d`/`Translation3d`, a `PhotonPoseEstimator` using `MULTI_TAG_PNP_ON_COPROCESSOR` with `LOWEST_AMBIGUITY` fallback, an `updatePoseEstimation(SwerveDrive)` that calls `swerveDrive.addVisionMeasurement(pose.estimatedPose.toPose2d(), pose.timestampSeconds, camera.curStdDevs)`, and a `VisionSystemSim` for simulation ([YAGSL-Example Vision.java](https://raw.githubusercontent.com/BroncBotz3481/YAGSL-Example/main/src/main/java/frc/robot/subsystems/swervedrive/Vision.java)). To use it here, change its parameter type from `swervelib.SwerveDrive` to `yams.mechanisms.swerve.SwerveDrive` (the 3-arg `addVisionMeasurement(Pose2d, double, Matrix<N3,N1>)` signature exists on the YAMS class, verified in the 2026.10.03 sources jar), add a 3-arg pass-through next to the 2-arg one at `SwerveDriveSubsystem.java:139-141`, swap the field layout from the 2025 Reefscape constant to `AprilTagFields.k2026RebuiltWelded` or `k2026RebuiltAndyMark` ([WPILib AprilTagFieldLayout](https://github.wpilib.org/allwpilib/docs/release/java/edu/wpi/first/apriltag/AprilTagFieldLayout.html)), and call `updatePoseEstimation` from `Robot.robotPeriodic()` or the subsystem's `periodic()`. PhotonVision recommends coprocessor multi-tag "for all teams as it will be the most accurate" ([PhotonVision: PhotonPoseEstimator](https://docs.photonvision.org/en/latest/docs/programming/photonlib/robot-pose-estimator.html)). One constraint discovered locally: YAMS constructs its `SwerveDrivePoseEstimator` with the default constructor, so state std devs are fixed at (0.1, 0.1, 0.1) and `SwerveDriveConfig` has no builder to change them; only the vision side is tunable, which is enough for the standard approach.

The std-dev recipe is where teams struggle most ("multi-tag filtering, prioritization, and standard deviation tuning ... a major struggle"), and the right starting point for a mid-sized team is the PhotonVision/YAGSL heuristic, not 6328's. The YAGSL example uses **(4, 4, 8) for single-tag and (0.5, 0.5, 1) for multi-tag**, rejects a single tag beyond 4 m by setting std devs to `Double.MAX_VALUE`, and otherwise multiplies by `1 + avgDist²/30` ([YAGSL-Example Vision.java](https://raw.githubusercontent.com/BroncBotz3481/YAGSL-Example/main/src/main/java/frc/robot/subsystems/swervedrive/Vision.java)). WPILib's guidance is to "make the vision heading standard deviation very large, make the gyro heading standard deviation small, and scale the vision x and y standard deviation by distance from the tag" ([WPILib: Pose Estimators](https://docs.wpilib.org/en/stable/docs/software/advanced-controls/state-space/state-space-pose-estimators.html)); Limelight's official values are (.7, .7, 9999999) for MegaTag2 ([Limelight: MegaTag2](https://docs.limelightvision.io/docs/docs-limelight/pipeline-apriltag/apriltag-robot-localization-megatag2)). 6328's formula, `xy = 0.01 * d^1.2 / n²` with theta trusted only for multi-tag, produces std devs around a centimeter and depends on high-resolution, well-calibrated cameras and strict rejection ([6328 2025 Vision.java](https://raw.githubusercontent.com/Mechanical-Advantage/RobotCode2025Public/main/src/main/java/org/littletonrobotics/frc2025/subsystems/vision/Vision.java)); graduate to it only after logging shows the camera noise justifies it (gerthworm's method: log vision x/y/rotation stationary at several distances and compute the actual noise, with "around 10cm" as a baseline) ([CD: Finding Standard Deviations](https://www.chiefdelphi.com/t/localization-finding-standard-deviations-for-setvisionmeasurementstddevs/496596)). Rejection filters belong in code regardless of vendor: zero tags, single-tag ambiguity above 0.4 (6328) to 0.7 (Limelight), single-tag average distance above 3–4 m, pose outside the field by more than 0.5 m, and frames captured while the gyro rate exceeds 360°/s ([Limelight: MegaTag2](https://docs.limelightvision.io/docs/docs-limelight/pipeline-apriltag/apriltag-robot-localization-megatag2)). WPILib also recommends "only adding vision measurements that are already within one meter or so of the current pose estimate" ([WPILib PoseEstimator](https://github.wpilib.org/allwpilib/docs/release/java/edu/wpi/first/math/estimator/PoseEstimator.html)). If continuous fusion proves unstable, 2910's fallback of hard-resetting odometry only during auto-align is simpler and worked at the top level.

The most common failure is a layout mismatch. 2026 has two field variants with separate AprilTag layouts, Welded (shipped by default) and AndyMark, and "It is very important to ensure that you use the correct field layout, both in the PhotonPoseEstimator and on the coprocessor" ([PhotonVision: MultiTag](https://docs.photonvision.org/en/latest/docs/apriltag-pipelines/multitag.html)); confirm which variant each event uses. Timestamps must be in the `Timer.getFPGATimestamp()` epoch, which PhotonLib's `EstimatedRobotPose.timestampSeconds` already satisfies. Draw vision poses on `drive.getField2d()` rather than a second `Field2d` ([YAGSL: Telemetry, Simulation & Vision](https://yagsl.yassrobotics.com/explanation/telemetry-and-vision.md)), and log a "vision rejected" count to the dashboard. In 2026's Rebuilt game (Fuel shot into a central hub, a Tower climb), the payoff from vision is distance-to-goal for shooter interpolation and reliable auto starts rather than sub-inch placement; no 2026 top-team vision write-ups were found, so that is an inference from the game design.

## A tuned drive-to-pose primitive beats a library of paths

The best-documented top-team auto is not a path library. 6328's 2025 `AutoBuilder.java` builds every auto from `new DriveToPose(drive, () -> {...goal...})` with goals computed from robot state, sequenced by sensor conditions such as `superstructure.hasCoral()` and `intake.isCoralIndexed()`, looped with `.repeatedly().until(...)`, and cut off at `autoDangerTime = 14.9` s rather than stepping through time-locked segments ([6328 AutoBuilder.java](https://raw.githubusercontent.com/Mechanical-Advantage/RobotCode2025Public/main/src/main/java/org/littletonrobotics/frc2025/commands/AutoBuilder.java)). Multiple other teams (2056, 3683, 4152) run "2056-style" PID drive-to-pose autos with large-tolerance transition waypoints ([CD: What do you use for autonomous?](https://www.chiefdelphi.com/t/what-do-you-use-for-autonomous/497145)). The shared pattern is vision-corrected pose plus a tuned drive-to-pose for every final approach, with pre-planned trajectories only for long transits, so the first game-agnostic milestone for 537 is a reliable `DriveToPose`, not a folder of paths.

YAMS already provides `SwerveDrive.driveToPose(Pose2d)` using the `PIDController`s configured at `SwerveDriveSubsystem.java:38-44` (P=4 translation, P=1 rotation), and YAGSL's how-to calls it "a good fit for short, single-target moves" with example tolerances under 2 inches and 5°, noting that the 0.1 m/s module velocity deadband leaves roughly 4.5° residual error at rotation kP 3 ([YAGSL: Drive to a pose](https://yagsl.yassrobotics.com/how-to-guides/drive-to-a-pose.md)); rotation P=1 is low by that standard and by 6328's 5.0. For a smoother, tip-safe version that respects the same acceleration limits as teleop, port 6328's structure into a new `commands/DriveToPose.java`: a linear `PIDController` (**kP 1.8, tolerance 0.01 m**) driven by a `TrapezoidProfile` (4.0 m/s, 3.5 m/s² teleop / 6.0 m/s² auto), a theta `ProfiledPIDController` (**kP 5.0, kD 0.5, tolerance 1.0°**) with continuous input, a feedforward scaler that fades the profile velocity between 0.01 and 0.05 m of error, and output via `ChassisSpeeds.fromFieldRelativeSpeeds(...)` to `setFieldRelativeChassisSpeeds` ([6328 DriveToPose.java](https://github.com/Mechanical-Advantage/RobotCode2025Public/blob/main/src/main/java/org/littletonrobotics/frc2025/commands/DriveToPose.java)). 2910's PID-with-friction-compensation is the simpler alternative and "definitely helped especially when we initiated auto align close to the end goal" ([Team 2910 Code Release 2025](https://www.chiefdelphi.com/t/team-2910-code-release-2025/503697)). Wrap it in a `DriveToNearestPose(List<Pose2d>)` command using `robotPose.nearest(...)`, which the community found cleaner than zone logic ([CD: one-button automatic alignment](https://www.chiefdelphi.com/t/reefscape-one-button-automatic-alignment/500045)); the list of poses is the only game-specific input, filled in at kickoff. Keep `AutoBuilder.pathfindToPose` (already configured) for long moves and drive-to-pose for the last meter, the combination 4915 found "extremely reliable" ([4915 Auto Align Whitepaper](https://www.chiefdelphi.com/t/4915-pathplanner-auto-align-whitepaper/494669)).

Stay on PathPlanner for pre-planned segments. It is "easier" and "sufficient for this year in 99% of cases" ([CD: Choreo Vs. Pathplanner](https://www.chiefdelphi.com/t/choreo-vs-pathplanner/492427)); Choreo's time-optimal trajectories executed 6–11% faster and let one team cut acceleration from 4.5 to 4.2 m/s² while keeping a 4-coral auto ([CD: Choreo vs. Pathplanner (Aug 2026)](https://www.chiefdelphi.com/t/choreo-vs-pathplanner/523324)), but "If you can't get PathPlanner to drive even slow paths accurately, Choreo will not be helpful" ([CD: PathPlanner vs Choreo](https://www.chiefdelphi.com/t/choreo-vs-pathplanner/467373)), and Choreo trajectories can be dropped into PathPlanner autos later via `PathPlannerPath.fromChoreoTrajectory()` with the caveat that they cannot regenerate from an off-nominal start ([PathPlanner: Choreo interop](https://pathplanner.dev/pplib-choreo-interop.html)). Choreo also faces a significant 2027 rework when WPILib moves the field origin to field center ([CD: Choreo 2026](https://www.chiefdelphi.com/t/choreo-2026/510723)). Keep the holonomic controller at the documented `PIDConstants(5.0, 0, 0)` starting point ([PathPlanner: Build an Auto](https://pathplanner.dev/pplib-build-an-auto.html)); community tuning puts translation P in the 2–10 range with a little D and no I ([CD: tuning PathPlanner](https://www.chiefdelphi.com/t/help-with-tuning-path-planner/515196)), and YAGSL's docs state PathPlanner's controller "never touches YAGSL's," so there is no need to match the YAMS gains. Register `NamedCommands.registerCommand(...)` in `RobotContainer` before any auto is built, because "any named command registered after path/auto creation will not be used" ([PathPlanner: Named Commands](https://pathplanner.dev/pplib-named-commands.html)), run `FollowPathCommand.warmupCommand()` at startup, and isolate alliance flipping behind one helper, both because the 2027 origin change will require rewriting it and because a 2025 bug saw red-alliance paths not mirrored when the flip supplier was evaluated at init before the Driver Station reported an alliance ([CD: Mirroring Path Problem](https://www.chiefdelphi.com/t/mirroring-path-problem-with-choreo-and-pathplanner/494094)).

Test every auto in simulation before the robot exists, then validate odometry scale on carpet. YAGSL simulates the whole swerve: call `drive.simIterate()` from `simulationPeriodic()` (currently empty in `Robot.java`), and `modules/pidfproperties_sim.json` overrides the real gains in sim ([YAGSL: Telemetry, Simulation & Vision](https://yagsl.yassrobotics.com/explanation/telemetry-and-vision.md)). Simulation cannot catch wrong wheel radius or module offsets, so run the AdvantageKit-documented checks on the real robot: rotate in place on carpet for wheel-radius characterization ("hard floors produce measurement errors"), measure true max speed until velocity plateaus, and compare measured vs setpoint module states ([AdvantageKit Spark swerve template](https://docs.advantagekit.org/getting-started/template-projects/spark-swerve-template/)), plus the 10 m straight-line test with vision disabled ([CD: Wrong Wheel Radius & Odometry](https://www.chiefdelphi.com/t/wrong-wheel-radius-odometry/517095)). Autos earn more than their raw points: in 2026 the match had a **20-second autonomous period** and "Based on the result of autonomous play, alliance hubs will alternate between active and inactive" for the whole teleop ([FIRST 2026 REBUILT overview](https://www.firstinspires.org/hubfs/web/volunteer/frc/2026-rebuilt-game-overview.pdf?hsLang=en)), and 254 listed "score 3+ Coral in auto" as a 2025 requirement for the ranking point ([254 2025 Tech Binder](https://media.team254.com/2025/09/985607eb-2025-Tech-Binder-254.pdf)). The specific 2026 point values circulating online (1 point per fuel, 15 for an auto L1 climb, 25-second shifts) come from a search aggregation and were not verified against the game manual.

## Build the offseason around habits that survive the 2027 control-system break

Three process layers cost about a day each and every elite repo has them. Add DogLog or Epilogue for mechanism logging; YAGSL's telemetry already publishes under `Mechanisms/<name>` and "is also written to a WPILib DataLog automatically" when `updateTelemetry()` runs each loop, with AdvantageScope as the recommended viewer ([YAGSL: Telemetry](https://yagsl.yassrobotics.com/explanation/telemetry-and-vision)). DogLog (581, used by 3847) offers imperative `DogLog.log()` with tunables and unit metadata, Epilogue (WPILib) auto-logs annotated classes but has no tunables, and AdvantageKit's purpose is replay ([DogLog FAQ](https://doglog.dev/getting-started/faq)); the Chief Delphi consensus is to "Start with DogLog or Epilogue for familiarity with logging concepts, then graduate to AdvantageKit's advanced features" ([CD: Doglog vs advantage kit](https://www.chiefdelphi.com/t/doglog-vs-advantage-kit/508842)). **Do not adopt AdvantageKit for replay on this codebase**: AdvantageKit's own documentation lists YAGSL (and CTRE Swerve) among "Large hardware libraries...which interact with hardware directly instead of through an IO layer" and recommends "the AdvantageKit swerve template project instead" ([AdvantageKit: Non-Deterministic Data Sources](https://docs.advantagekit.org/getting-started/common-issues/non-deterministic-data-sources/)); replay would mean replacing the only subsystem the team has. Logging-only AdvantageKit, as 2910 does, is possible but adds cost without replay. Copy 3847's conventions, `Subsystem/Name` keys with units as metadata, NT mirroring off on the robot and forced off under FMS, console capture on, "Log inside `periodic()`" ([Spectrum logging.md](https://github.com/Spectrum3847/2026-Spectrum/blob/main/docs/tools/logging.md)). Build the driver dashboard in Elastic, which launches from the WPILib VS Code palette and deactivates camera streams when unused ([WPILib Elastic](https://docs.wpilib.org/en/stable/docs/software/dashboards/elastic.html)), not Shuffleboard, because 2027 removes Shuffleboard and SmartDashboard and replaces `SendableChooser` with `Selectable` ([WPILib New for 2027](https://docs.wpilib.org/en/latest/docs/yearly-overview/yearly-changelog.html)); keep the auto chooser at `RobotContainer.java:46-47` behind one small class for that reason. Then add CI: branch protection on `main`, PRs, a GitHub Actions workflow in the shape of 1678's `tests.yml` running `./gradlew build` (then `test`), and Spotless applied on build as 3847 does. FRC 157, a mid-tier team, reported exactly this set (Epilogue, PRs, branch protection, Actions, templates, a team package namespace) as transformative in its 2026 build thread ([FRC 157 2026 Build Thread](https://www.chiefdelphi.com/t/509425)).

Make simulation the default workflow and write the superstructure skeleton before the game is known. 3847 runs sim "on every change: it catches state machine bugs, wiring mistakes between subsystems, and trajectories that look fine in the editor and cannot actually be driven" ([Spectrum simulation.md](https://github.com/Spectrum3847/2026-Spectrum/blob/main/docs/tools/simulation.md)), and mid-tier teams 3506, 3749, and 157 used sim as their main rookie-training and driver-practice vehicle ([CD: 3506 build thread](https://www.chiefdelphi.com/t/511666)). YAMS supports arms, elevators, pivots, turrets, and flywheels with `simIterate()` physics, battery simulation for brownout detection, and a YAMG form-based code generator ([YAMS docs](https://yams.yassrobotics.com/)); generate one practice elevator or arm, wire its `simIterate()` into `Robot.simulationPeriodic()`, and visualize it in AdvantageScope with CAD. For architecture, 3847's pattern is the most approachable: each mechanism is "a single file that carries the mechanism, its inner `Config` class, and its inner `WantedState` and `SystemState` enums," a `SuperStructure` orchestrator handles coordinated moves as entries in a `WantedSuperState` enum via `handleStateTransition()` and `applyStates()`, "Which button fires which state is in `Robot.configureBindings()`, and only there," and the same code runs on multiple robots by switching on roboRIO serial ([Spectrum 2026-season-specific.md](https://github.com/Spectrum3847/2026-Spectrum/blob/main/docs/other-guides/2026-season-specific.md)). 971 teaches superstructure logic before the drivetrain in its 2026 curriculum and requires "Test in sim when possible before asking for review" ([frc971/training-2026](https://github.com/frc971/training-2026)). Unit tests should target pure logic (state transitions, targeting geometry, alliance flipping) using `HAL.initialize(500, 0)` and the sim classes, not hardware ([WPILib unit testing](https://docs.wpilib.org/en/stable/docs/software/wpilib-tools/robot-simulation/unit-testing.html)).

The 2027 transition shapes what is worth building now. "RoboRIO will not be legal for competition in 2027" and every team receives a SystemCore in the 2027 kit of parts, with software not ready "until the kickoff release" ([CD: Systemcore onsale date](https://www.chiefdelphi.com/t/systemcore-onsale-date/517572)). WPILib 2027 requires Java 25, renames `edu.wpi.first` to `org.wpilib`, adds Commands v3 and an OpMode framework, removes `robotInit()`, introduces a `CANPort` enum and a Telemetry/Tunables API, moves the field origin to field center, and renames `ChassisSpeeds` to `ChassisVelocities` ([WPILib New for 2027](https://docs.wpilib.org/en/latest/docs/yearly-overview/yearly-changelog.html); [YAGSL: Set up PathPlanner](https://yagsl.yassrobotics.com/how-to-guides/setup-pathplanner.md)). YAGSL and YAMS already target "WPILib 2027 (`2027_alpha7`, Java 25)" on SystemCore with both Commands v2 and v3, and have a schema-migration page ([YAGSL docs](https://yagsl.yassrobotics.com/)); PathPlannerLib has a `2027.0.0-alpha-4` ([YAGSL: Set up PathPlanner](https://yagsl.yassrobotics.com/how-to-guides/setup-pathplanner.md)); 3847 has already converted a 2026 robot to SystemCore for an October 2026 event ([Spectrum3847/2026-FM-SystemCore](https://github.com/Spectrum3847/2026-FM-SystemCore)). WPILib's lead stated the 2027 API changes are "not going to change _significantly_" from the alphas ([CD: Programming changes for 2027](https://www.chiefdelphi.com/t/programming-library-changes-for-2027/519900)). The implication is to keep offseason work in architecture and habits (state machine, logging, sim, CI, vision fusion, drive-to-pose), favor command factories and Triggers over subclassed v2 Commands, and schedule a December port. The official 2027 beta-program dates and vendor (CTRE/REV) SystemCore library status were not confirmed from primary sources and should be checked before scheduling.

## Conclusion

The single most important reframing for a team that is "not sure where to start" is that the hard-to-beat capabilities (auto-align, dynamic targeting, multi-piece autos) are cheap once a trusted pose and a drive-to-pose primitive exist, and nearly impossible without them. Every hour spent on vision fusion and odometry validation this fall pays back in every subsystem written in January, whereas game-specific paths and mechanism code written now will be rewritten. The codebase's hooks (`addVisionMeasurement`, `AutoBuilder`, `driveToPose`, `photonlib`) mean the team is a camera purchase and a few hundred lines away from the first of those layers.

The two risks that deserve a decision rather than a workaround are the mixed Kraken/NEO drive motors and the 2027 control-system break. The motor mix has no public precedent, forces a single shared PID file to serve two very different velocity loops, and caps the chassis at the weaker motor; matching all four drive motors is the lowest-risk fix and should be weighed against the tuning effort before the season starts. The 2027 break is certain and already supported by YAGSL/YAMS, so a December port is the difference between arriving at kickoff with a working SystemCore project and spending week one of build season on a package rename.
